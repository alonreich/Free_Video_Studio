## build/FvsBuild/CodeSigning.cs

### CodeSigning — SIGNMANDATE_01, ISSUE_03, UPDATETRUST_01 (line 6)

SIGNMANDATE_01 - Authenticode signing. Set FVS_SIGN_PFX and FVS_SIGN_PASS to activate; the
password is read from the environment, never hardcoded. The RFC-3161 timestamp is mandatory:
without it every shipped copy stops validating the day the certificate expires.

=============================================================================================
SIGNING IS NO LONGER OPTIONAL BY DEFAULT, AND UNSIGNED IS NO LONGER SILENT.

This method used to return true with an informational line when FVS_SIGN_PFX was unset, so the
normal outcome of running Build.cmd on a machine without a certificate was a shipped, unsigned
release - and the log line saying so scrolled past between two hundred others.

Two things depend on that signature, and both were quietly disarmed:
  1. SmartScreen. An unsigned download gets the full "Windows protected your PC" wall, and the
     Win32 metadata block in the .csproj (ISSUE_03) exists precisely so the user has something
     reassuring to read at that moment. Unsigned, the reassurance is a publisher field with no
     cryptographic backing.
  2. UPDATETRUST_01. AuthenticodeVerifier pins an update against the RUNNING executable's
     publisher. An unsigned running executable is not an anchor, so the pin degrades to
     hash-only - and the hash comes from the same GitHub JSON document that supplies the
     download URL. Whoever controls that response controls the payload and its fingerprint in
     one move, and the payload is launched with --install --auto-update, i.e. elevated.
     That is the attack AuthenticodeVerifier was written to close, and shipping unsigned is
     what holds it open.

So: no certificate configured is now a BUILD FAILURE. An operator who genuinely wants an
unsigned artifact - a local smoke test, a CI job that signs in a later stage - sets
FVS_ALLOW_UNSIGNED=1 and gets a loud, explicit, recorded acknowledgement instead of a default.
Spec: docs/05_SYSTEM_LIFECYCLE_STORAGE.md section 5 (SYS-SIGNING).
=============================================================================================

If FVS_SIGN_PFX is set but signing fails, the build fails - silently shipping an unsigned
binary when the operator asked for a signed one remains the worst outcome of all.

### CodeSigning.SignDependenciesWhenPubliclyTrusted — SIGNDEPS_01 (line 156)

SIGNDEPS_01 — signs the bundled third-party programs and libraries (FFmpeg, ffprobe, mpv and
their DLLs) in staging, but ONLY with a publicly trusted certificate (FVS_SIGN_PFX).

WHY: Smart App Control, the "prevalence" attack-surface-reduction rule and company allow-lists
judge every .exe and .dll on its own. An unsigned FFmpeg is blocked even when the app is allowed,
and the app then opens with a dead preview or a failing export.

WHY NOT WITH THE REPOSITORY CERTIFICATE: these files are the upstream builds, byte for byte, and
Microsoft's cloud may already know those exact bytes (reputation is per file hash). Signing them
with a certificate nobody else trusts would change every hash, throw that reputation away and
gain nothing, so without FVS_SIGN_PFX they are left exactly as published. Files that already
carry a valid signature are never re-signed. Spec: 05 SYS-SIGNING.

### CodeSigning.EnsureLocalLeaf — UPDATEPIN_02 (line 279)

## build/FvsBuild/PeIdentity.cs

### PeIdentity — PEIDENTITY_01 (line 5)

PEIDENTITY_01 — the shipped program must introduce itself under its OWN file name.

NativeAOT copies the Win32 version resource from the managed assembly, so
`FreeVideoStudio.exe` said `OriginalFilename = FreeVideoStudio.dll` and
`InternalName = FreeVideoStudio.dll`. A program whose version resource names a different file
than the one on disk is the "renamed binary" masquerading pattern (MITRE T1036.003) that antivirus
engines score. The SDK has no property for these two strings, so the build rewrites them in the
version resource itself, BEFORE signing (the signature covers the result).

The change is in place and length-preserving: ".dll" and ".exe" have the same length, so no
resource offset, size or checksum moves. Only the VS_VERSION_INFO block inside the .rsrc section is
touched; nothing outside it can be changed by this code. Idempotent: a correct file is left alone.

## build/FvsBuild/ReleaseChecklist.cs

### ReleaseChecklist — NEWRELEASE_01 (line 9)

NEWRELEASE_01 — after a SUCCESSFUL publish (Build.cmd only; never --dev or --no-publish), prepare
everything docs\New-Release.md asks the human to do, then open that checklist in Notepad++.

Why: a brand-new file has no reputation, so Microsoft Defender's cloud AI may flag it in its first
days. The free remedy is a manual false-positive submission to Microsoft (WDSI), which has no free

(~62 MB, ~25 MB zipped) can. This class makes that upload a two-minute job:

Nothing here can fail the build: a release is already public when this runs. Any problem is a
warning, and the checklist still opens.

### ReleaseGate — RELGATE_01, RELNOTES_02 (line 16)

RELGATE_01 — THE GATE IN FRONT OF A PUBLIC RELEASE (09 DIST-RELEASEGATE).

⚠️ WHY IT EXISTS. `Build.cmd` used to publish whatever was on disk: it never checked that
the working tree was committed or pushed, it rewrote five version files and left them
uncommitted, and it asked GitHub to tag "the default branch" — the remote HEAD, not the commit
that was built. A release could therefore ship code that exists in no commit, under a tag that
points at different code, while the repository's own version files fell behind every release.

The release is now a short, ordered transaction. Nothing outside obj\ and compiled\ changes
until `Preflight` has proven the starting point is exact:

- `Preflight` — touches nothing. Clean tree (tracked AND untracked), on the default
  branch (stable) and exactly equal to its remote, the tag unused locally and on GitHub, the GitHub
  CLI signed in, user-facing notes present and lint-clean (RELNOTES_02), then an explicit
  confirmation (type PUBLISH, or `--yes` when there is no terminal).
- `CommitVersion` — writes the version files, commits ONLY them as
  "release: vX", and creates an annotated tag on that commit. The build then compiles that commit.
- Build. Any failure → `Undo`: the commit and tag are removed and the tree is
  exactly as the developer left it (safe because step 1 proved it was clean).
- `TreeStillClean` — the build must not have changed a tracked file, or the binary
  would not be the tagged source.
- `PushRelease` — pushes the commit and tag atomically. Failure → `Undo`.
- `GitHubReleasePublisher` creates the release from that tag (`--verify-tag`).
- `RecordReleaseNotes` (stable only, after a successful publish) — promotes
  `## Upcoming` / `## Unreleased` to the new version in docs/CHANGELOG.md and docs/changes.md,
  prunes them to their retention, commits "docs: release notes for vX" and pushes. Done last on
  purpose: a failed publish leaves the notes in Upcoming for the next attempt.

## build/FvsBuild/SmartUpdateBuilder.cs

### SmartUpdateBuilder — BINDELTA_01, NODROPPER_01, DELTABASE_01 (line 6)

DIST-SMART / BINDELTA_01 — produces what lets an update download only what changed:

- obj\ReleaseAssets\smart\f-<sha256>.br — every installed file, Brotli-compressed, named by
  its CONTENT (the same name always means the same bytes);
- obj\ReleaseAssets\smart\p-<from>-<to>.patch — binary patches turning recent versions'
  FreeVideoStudio.exe into this one (only when clearly smaller than the compressed file);
- obj\ReleaseAssets\update.json + update.sig.json — the list, signed with the publisher key.
- NODROPPER_01 — a second signed copy of the same list WITHOUT the full-installer entry (the
  installer cannot name its own hash), packed into the Inno Setup installer beside the files. The
  elevated worker installs from it exactly as from a smart update.

Patch bases come from obj\ReleaseHistory\<version>\ (the signed program file of earlier builds).
A release build patches from the last versions that were actually PUBLISHED; a dev build from the
last builds of any kind, so dev_build.cmd + dev.cmd exercise the same path (D1).

DELTABASE_01 — before a release build makes its patches, `EnsurePublishedBases`
makes sure the program file of each of the last `PatchBases` PUBLISHED releases is in
that history and marked released: it reads each release's signed update.json, takes the program's
SHA-256 from it, and either marks a matching local copy as released or downloads that release's
own content-addressed program asset (`f-<sha>.br`) and verifies it. It used to run only when
the history folder was empty, and then fetched the release asset named `FreeVideoStudio.exe` —
which is the INSTALLER under its pre-Inno alias, not the program — so a release patched from a
file no installed copy has, or (with only unmarked local builds) from nothing at all.

### near MAX_CONSECUTIVE_GAP (line 101)

══════════════════════════════════════════════════════════════════════════════════════════
FUZZY MATCHING — "these two blocks are ~85% the same", not just "identical".

THE PROBLEM WITH EXACT-ONLY. Growth used to stop dead at the first line whose shape differed.
Two 40-line blocks that are identical EXCEPT one line in the middle were therefore reported as
two short matches — or, if either half fell under the 6-line floor, as nothing at all. The tool
under-reported exactly the near-copies a human most wants to see.

WHAT HAPPENS NOW. A match still has to START on a solid seed of SEED_LINES identical lines —
that seed is what makes the search fast, because identical seeds can be found with a hash
lookup instead of comparing everything to everything. From that seed the block grows in BOTH
directions, and a differing line no longer stops it: it is counted as a miss and growth
continues, as long as
    (a) the running score  matched / total  never falls below MIN_SIMILARITY, and
    (b) no more than MAX_CONSECUTIVE_GAP differing lines appear back to back.
Rule (b) is what stops two unrelated regions being welded together by a long shared tail.

⚠️ WHAT THIS STILL CANNOT SEE. Two blocks that are 85% alike but never share SEED_LINES
identical lines in a row are invisible, because nothing seeds them. Catching those needs
all-pairs alignment, which is orders of magnitude slower. This is a deliberate trade.

⚠️ SUBSTITUTIONS ONLY, NOT INSERTIONS. The two sides advance in lockstep, so a block with an
extra line inserted on ONE side scores badly from that point on. Reported similarity is
therefore a LOWER BOUND — the real resemblance can be higher, never lower.
